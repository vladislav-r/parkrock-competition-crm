# Исправления после нагрузочной проверки — 6 сентября 2026

**На изолированном стенде с четырьмя процессами API целевые 100 запросов/с обработаны в трёх минутных сценариях. Зависание устранено; HTTP 5xx, тайм-аутов основной нагрузки и пропусков генератором в итоговых прогонах нет. Подтверждённые изменения сохранены. При обрывах остаются неприменённые команды с конфликтом версии: гарантии автоматической доставки любого изменения пока нет.**

Это результат локальных изменений и проверки отдельного стенда. Развёртывание на VPS не выполнялось. Обычный локальный запуск с `--reload` остаётся однопроцессным.

## Условия и результат

100 запросов/с суммарно, восемь виртуальных клиентов, 806 участников в отдельной копии PostgreSQL. Профиль: GET 60%, PUT 20%, PATCH 10%, POST 5%, DELETE 5%. Каждый профиль длится 60 секунд, после него завершаются уже отправленные запросы и отдельно проверяются повторы. Хорошая связь: около 20 мс и 100 Мбит/с на клиента; слабая: 400–500 мс и 2 Мбит/с, задержка отправки тела для 512 Кбит/с; смешанная: четыре клиента каждого типа. Слабым клиентам намеренно обрывается соединение до отправки в API и после получения ответа API. Подробные ограничения эмулятора описаны в [исходном отчёте](../load-2026-09-06/REPORT.md).

| Показатель | Хорошая | Слабая | Смешанная |
|---|---:|---:|---:|
| Запланировано | 6000 | 6000 | 6000 |
| HTTP 200 с первой клиентской попытки¹ | 6000 | 5813 | 5909 |
| HTTP 409 в основном прогоне | 0 | 37 | 17 |
| Искусственные обрывы, замеченные клиентом | 0 | 138 | 67 |
| DELETE без подтверждённого POST, не отправлены | 0 | 12 | 7 |
| HTTP 5xx / тайм-ауты / отбрасывание генератором | 0 / 0 / 0 | 0 / 0 / 0 | 0 / 0 / 0 |
| p95 успешных ответов, мс | 225 | 796 | 705 |
| p95 задержки запуска запроса генератором, мс | 22,51 | 16,55 | 16,77 |
| Подтверждённые изменения до восстановления | 2400 | 2250 | 2327 |
| Отсутствующие или несовпадающие подтверждённые операции | 0 | 0 | 0 |
| Ответы при восстановлении: 200 / 409 | — | 89 / 49 | 43 / 23 |

¹ Одна операция aiohttp может автоматически повторять идемпотентный HTTP-метод при разрыве соединения; повтор использует тот же идентификатор операции. Поэтому число обращений к API и число искусственных обрывов прокси могут превышать число логических клиентских запросов. p95 рассчитан по успешным ответам, включая эмуляцию связи; восстановление выполнялось после основной нагрузки и в p95 не включено. DELETE, ожидающий неподтверждённый POST, нельзя считать успешно выполненным запросом. При слабой и смешанной связи это соответственно 5988 и 5993 реально сформированные операции из 6000 позиций нагрузки.

После каждого прогона API перезапускался. Все подтверждённые ответы сопоставлены с сохранённым `OperationRecord.response_json`; пропусков и несовпадений нет. Повторены все неизвестные по результату и отклонённые изменения. В слабом профиле 76 из 89 ответов 200 при восстановлении вернули ранее сохранённый результат операции; в смешанном — 37 из 43. Восстановление итоговых прогонов прошло без сетевых ошибок.

**49 и 23 ответа 409 при восстановлении — оставшийся риск доставки, а не успешное сохранение.** Клиент повторяет устаревшую версию после других изменений того же участника. Сервер правильно запрещает перезапись более нового состояния. Автоматическое разрешение таких конфликтов требует отдельного правила выбора данных; молча менять `expected_version` и повторять старую команду нельзя. Ни браузерная очередь, ни её поведение после закрытия вкладки здесь не проверялись.

## Что исправлено

1. **P0, исчерпание потоков и соединений.** Ожидание допуска к DB-сессии теперь асинхронное и начинается до авторизации. На процесс допускаются 12 запросов к базе при пределе пула 15; место освобождается после закрытия сессии, в том числе при отмене запроса. При ожидании свыше 5 секунд API отвечает 503 с `Retry-After`. Запись отказов в аудит вынесена из цикла событий. Контроль с маленьким пулом и отменой запросов включён в тесты.
2. **P1, лишние SQL.** Счётчики сетов агрегируются одним запросом; возрастные группы и прохождения участников загружаются пакетно. Дополнительно найден и устранён N+1 в чтении возрастных категорий. Публичные результаты выбирают нужные поля прохождений без создания лишних ORM-объектов.
3. **P1, конфликты независимых судей.** Блокировки берутся в одном порядке: категория, затем результат. Версия финального результата меняется при изменении исходных попыток, а пересчёт места соседнего финалиста не создаёт ложный конфликт. Первая запись судьи на назначенную трассу защищается наличием попытки на этой трассе; администратор при замене результатов по-прежнему обязан предъявить актуальную версию.
4. **P1, процессорная нагрузка и трафик.** Включено HTTP gzip. Production запускается через `app.serve` с четырьмя процессами по умолчанию, поскольку один процесс после SQL-оптимизаций всё ещё не обеспечивал целевой поток. Предел задаётся `WEB_CONCURRENCY=1..4`; четыре пула допускают до 60 соединений PostgreSQL суммарно.
5. **Согласованная работа процессов.** Prometheus объединяет счётчики всех процессов; ресурсные показатели обновляются ежесекундно. После аварии процесса удаляются его активные gauge-метрики, накопленные счётчики сохраняются. Резервное копирование, восстановление и связанные операции используют общий файловый замок; отметка успешной почасовой копии предотвращает последовательное создание четырёх одинаковых копий. Логи получают PID, чтобы процессы не ротировали один файл одновременно.

Миграция структуры базы не требуется. Режим разработки с автоматической перезагрузкой сохранён; новый запуск и ограничения описаны в [README](../../README.md). Многопроцессный сбор использует предусмотренный библиотекой режим с отдельным каталогом и коллектором; совместное использование `--reload` и нескольких workers не поддерживается Uvicorn. [Prometheus client Python](https://github.com/prometheus/client_python/blob/master/docs/content/multiprocess/_index.md), [Uvicorn](https://www.uvicorn.org/deployment/).

## Сильные стороны после исправлений

- На хорошем соединении все 6000 запросов, включая 2400 изменений, завершились успешно. Все проверки `/health` основной нагрузки прошли.
- При слабой связи сервер продолжает работать; подтверждённые операции переживают перезапуск и возвращаются при повторе с тем же ID.
- В каждом профиле восемь одновременных повторов одной команды дали восемь одинаковых успешных ответов. Восемь разных команд с одной исходной версией дали одну успешную запись и семь защищающих данные конфликтов.
- В отдельном финальном сценарии потеря ответа после записи не создала дубликатов: восемь повторов успешны, у каждого из 16 тестовых финалистов ровно одна попытка на проверяемой трассе. Восемь независимых параллельных судейских записей в одну категорию успешны, вместо прежних двух из восьми.
- Проверены замена аварийно завершённого процесса, сохранение общих счётчиков, очистка его активных метрик и штатное завершение запусков с одним и четырьмя процессами.

Времена — отдельные измерения функций без HTTP и фоновой нагрузки; состав прохождений в тестовой копии менялся, поэтому это не строгий сравнительный benchmark времени. Уменьшение числа SQL подтверждено отдельным регрессионным тестом. Полный список не входил в основной поток нагрузки и остаётся большим: около 1,64 МБ до сжатия. Пагинация пока не добавлялась.

По Prometheus с шагом 5 секунд в итоговых окнах: среднее потребление API 2,7–2,9 процессорного ядра, суммарная память процессов до 532 МиБ; соединения тестовой базы — до 22, занятые соединения пула API — до 15. В собранных отсчётах очередь допуска равна нулю, deadlock PostgreSQL не зарегистрированы. Короткие пики между отсчётами не исключены. За профиль через эмулятор передавалось около 21 МиБ сжатых ответов суммарно на восемь клиентов. Ресурсы PostgreSQL, генератора и других приложений не входят в показатели памяти и CPU API.

## Что делать дальше и в каком порядке

1. **P1 — явное разрешение конфликтов при восстановлении связи.** Сохранить исходную непринятую команду, показать текущее состояние и выбор пользователя; использовать существующие `X-Operation-Id`, `expected_version` и ответ `409`. Критерий: ни один конфликт не исчезает без решения, очередь переживает перезапуск клиента. Это отдельная проверка клиентской очереди, выходящая за нынешнее ограничение «только API/нагрузка». Правило автоматического выбора между старым и новым значением требует согласования.
2. **P1 — приёмка на целевом сервере.** Развернуть подготовленный запуск в тестовом окружении VPS и повторить минимум 30 минут при 100 запросах/с, затем проверить ступени нагрузки и восстановление. Инструменты: сохранённый генератор или k6, сетевой прокси/Toxiproxy, Prometheus/Grafana. Контроль: HTTP 5xx, p95/p99, CPU, память, очередь DB, проверка каждой подтверждённой операции. Минутные локальные прогоны не доказывают отсутствие утечек и достаточность ресурсов VPS, HTTPS-прокси или реальной мобильной сети.
3. **P2 — ограничить стоимость больших чтений.** Добавить пагинацию списка участников и при необходимости условные ответы/версионированный кэш публичных результатов. Сохранить корректное обновление после результатов и смены этапа. Измерять SQL-профилем и тем же нагрузочным сценарием; сейчас основной запас ограничивается CPU, а не числом запросов к БД.
4. **P2 — эксплуатационные алерты и хранение логов.** Добавить правила по 5xx/503, p95, ожиданию DB и недоступности API; определить получателя уведомлений. Новые DB-метрики уже доступны, правила уведомлений не настроены. Нужна также очистка файлов логов старых PID после перезапусков: ротация ограничивает каждый файл, но не общее число PID-файлов.
