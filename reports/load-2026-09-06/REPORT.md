# Нагрузочная проверка ParkRock Hub — 6 сентября 2026

**Результат: текущий локальный backend не выдержал смешанную нагрузку 100 запросов/с.** Отказ воспроизводится и на хорошем соединении, и без сетевого эмулятора. Обнаружены блокировка обработки запросов и излишние конфликты при одновременной работе судей. Подтверждённые записи в проверенных случаях не потерялись, но гарантировать доставку всех изменений при плохой связи пока нельзя.

## Условия и границы проверки

- 100 запросов/с **суммарно**, восемь виртуальных клиентов примерно по 12,5 запроса/с. Это не восемь физических телефонов и не 800 запросов/с. Число одновременных незавершённых запросов меняется с задержкой.
- Копия рабочей PostgreSQL, отдельный API на порту 18082. Рабочий API на 8001 не участвовал в изменяющей нагрузке. В копию добавлены 800 вымышленных участников: всего 806 участников, 20 квалификационных трасс; исходно 10 сетов и один тестовый. Создаваемые нагрузкой пустые сеты могли временно увеличивать их количество.
- Windows, Python 3.14, FastAPI 0.116.1, SQLAlchemy 2.0.43, PostgreSQL 16 в Docker; один процесс Uvicorn. На компьютере 12 логических процессоров и 15,4 ГиБ RAM. Генератор, API и Docker работают на одном компьютере вместе с другими приложениями. Это проверка текущей локальной конфигурации, не аттестация VPS, HTTPS-прокси или production-контейнера.
- Профиль запросов: GET 60%, PUT результатов квалификации 20%, PATCH статуса оплаты 10%, POST пустого сета 5%, DELETE созданного сета 5%. DELETE зависит от успешного POST. GET: публичные результаты, административная сводка, поиск участников, категории, текущий пользователь. Методы распределены между восемью клиентами не полностью одинаково.
- Хорошая связь: добавленная задержка примерно 20 мс, загрузка до 100 Мбит/с на клиента. Слабая: около 400–500 мс, загрузка 2 Мбит/с, задержка отправки тела рассчитана для 512 Кбит/с. Ограничение скачивания общее для запросов одного клиента; отправка тела моделируется отдельно, не полноценным общим uplink-шейпером. Смешанный профиль: четыре хороших и четыре слабых клиента.
- Сетевой прокси моделирует ограничения HTTP и обрывы соединения, а не физическую радиосеть и потерю отдельных TCP-пакетов. Запланированы обрывы до пересылки каждого 97-го запроса слабого клиента и после ответа каждого 31-го изменяющего запроса. В коротких перегруженных прогонах не все запланированные разновидности сбоев успели проявиться; потеря ответа после commit дополнительно проверена отдельным сценарием.
- Использованы Python asyncio/aiohttp, HTTP-прокси с ограничением канала, PostgreSQL, отдельный временный Prometheus со сбором каждые 5 секунд, снимки стеков Python. Интерфейсы и браузерная очередь не тестировались.

## Измеренные результаты

Сначала прошёл базовый прогон 10 запросов/с: **300 из 300 ответов HTTP 200 за 30 секунд**. Он слишком короткий, чтобы считать 10 запросов/с доказанным длительным пределом системы.

Первый исследовательский прогон 100 запросов/с был прерван: завис API и накопилась очередь HTTPX-генератора. Его сырые данные сохранены, но из него не выводится точная пропускная способность. Затем выполнены независимые ограниченные прогоны aiohttp с перезапуском только тестового API между сценариями.

| Связь | Запланированные позиции до остановки | HTTP 200 | HTTP 502 от тестового прокси | Тайм-ауты клиента | Обрывы | Не допущены генератором | DELETE без успешного POST |
|---|---:|---:|---:|---:|---:|---:|---:|
| Хорошая | 1505 | 28 | 546 | 2 | 0 | 897 | 31 |
| Слабая | 1504 | 30 | 397 | 125 | 6 | 916 | 29 |
| 4 хороших + 4 слабых | 1506 | 27 | 474 | 67 | 0 | 908 | 29 |

В каждом сценарии выдача нагрузки остановлена приблизительно через 15 секунд после трёх подряд неуспешных проверок `/health`; с ожиданием запросов и остановкой процесса — около 22,65 секунды. Планировалось 60 секунд, но продолжать заведомо зависший сценарий было бессмысленно. В числе запланированных позиций есть одна пограничная позиция проверки остановки, поэтому оно на единицу больше суммы исходов.

**502 в таблице создал тестовый прокси при отсутствии ответа upstream; это не HTTP 502, возвращённые FastAPI.** Недопущенные позиции — защитный предел генератора в 256 незавершённых операций, не потерянные сервером записи. Они отдельно учитываются как невыполненная целевая нагрузка. p95 задержки запуска допущенных запросов — 13,5–14,4 мс: повторный генератор своевременно создавал нагрузку до достижения своего защитного лимита.

Из-за ранней блокировки эти результаты не дают честной оценки «максимум N запросов/с», длительного p95 исправно работающей системы или отдельной цены плохого интернета. Они дают воспроизводимый отрицательный результат для цели 100 запросов/с. p95/p99 наблюдавшихся ответов и тайм-аутов по методам сохранены в `bounded-summary.json`; усечённые тайм-аутом распределения нельзя трактовать как задержки успешно выполненных запросов.

## Главные слабые места

### 1. Блокировка обработки запросов и жизненного цикла DB-сессий — критично

В момент зависания **все 40 рабочих потоков AnyIO ожидали выдачи соединения SQLAlchemy**. PostgreSQL показывал **15 соединений `idle in transaction`**, ожидающих клиента, вместо активного исполнения тяжёлых SQL. В первом прогоне эти транзакции оставались открыты больше 110 секунд. Зафиксирована ошибка `QueuePool limit of size 5 overflow 10 reached ... timeout 30.00`.

Prometheus подтверждает зависание API: target перестаёт отвечать на scrape, тогда как exporter PostgreSQL остаётся доступным. В эксперименте с расширенным пулом застыли уже 64 транзакции. Счётчик PostgreSQL deadlocks за сохранённый интервал оставался нулевым: речь об ожидании ресурсов приложения, а не обнаруженном PostgreSQL взаимном блокировании строк.

Точное место, из-за которого удерживаются сессии и исчерпываются рабочие потоки, ещё требует исправления и регрессионного подтверждения. Проверять нужно совместно `backend/app/db.py`, цепочки синхронных зависимостей FastAPI, сериализацию и освобождение сессий. Эксперименты **не подтверждают** совет просто увеличить пул, количество потоков или добавить произвольный семафор.

Наблюдаемый RSS API в доступных scrape — примерно 112–171 МиБ; в зависании метрики пропадают, поэтому это не гарантированный максимум памяти. Нехватка RAM или мощности PostgreSQL не доказана.

### 2. Лишние конфликты при работе судей — высокий приоритет

В отдельном сценарии судейского API восемь параллельных PUT относились к **разным финалистам одной категории**. Сохранились **2 из 8**, остальные **6 вернулись с HTTP 409 `edit_conflict`**; для них записей попыток в базе не оказалось.

В `recalculate_final_category()` пересчитываются и обновляются места нескольких финалистов, участвующих в общей версии результата. Это вероятный источник конфликтов между независимыми записями; требуется разделить версию исходного результата трассы и версию производного рейтинга либо сериализовать пересчёт категории с корректной повторной обработкой.

По чтению существующего кода очереди судьи, такой 409 сохраняет запись в локальной очереди и предлагает обратиться к главному судье, если сервер не содержит совпадающего заблокированного результата. Автоматическое обновление ожидаемой версии в этом пути отсутствует. Это вывод из исходников, не результат испытания браузера. Получается риск **недоставленных результатов**, даже когда интерфейс продолжает хранить черновик.

### 3. Много SQL и большие ответы — высокий приоритет

Измерения реальных функций обработчиков в изолированной базе, без фоновой нагрузки и HTTP-накладных расходов:

| Обработчик | SQL на вызов | Время одного замера | Размер JSON |
|---|---:|---:|---:|
| Публичные результаты | 30 | 97 мс | 288 КБ |
| Административная сводка | 27 | 33 мс | 7 КБ |
| Поиск 10 участников | 23 | 37 мс | 20 КБ |
| Полный список 806 участников | **1615** | **1,72 с** | **1,65 МБ** |

Полный список не входил в основной поток запросов; он измерен отдельно как потенциально более тяжёлый реальный сценарий. Причина количества запросов видна в построчном чтении категории/результатов участника; для сетов отдельно считаются два счётчика на каждый сет. Нужны пакетные выборки, агрегация и пагинация, а не подбор индексов наугад.

При запланированных 10 полных ответах публичных результатов в секунду только они дают около **23 Мбит/с** несжатого трафика. Совокупный канал восьми слабых клиентов — 16 Мбит/с. Даже после устранения блокировки такой профиль не помещается в слабую сеть без сокращения трафика. Для одного фактического ответа локальное gzip-сжатие уменьшило 288 172 байта до 28 807 байт; это оценка потенциала, а не измерение уже включённого HTTP-сжатия.

## Сохранность данных и сильные стороны

- В трёх ограниченных смешанных прогонах отправлено **632 изменяющие команды**. Получены и сверены с `operation_records` **27 подтверждённых ответов**: отсутствующих записей или несовпадений ответа не обнаружено.
- После перезапуска тестового API повторены **605 неподтверждённых команд с теми же идентификаторами и телами**: 581 завершилась HTTP 200, 24 — HTTP 409. Три успешно повторённые команды уже были записаны до потери подтверждения. Эти 24 конфликта **не считаются успешно доставленными данными**.
- В каждом из трёх прогонов восемь конкурентных повторов одной команды с одним `X-Operation-Id` вернули одинаковые HTTP 200. Восемь разных команд с одной ожидаемой версией дали ровно один успех и семь 409: скрытого затирания изменений не наблюдалось.
- Для восьми отдельных судейских результатов соединение принудительно закрывалось **после получения прокси успешного ответа API**. Все восемь явных повторов завершились HTTP 200; в базе ровно по одной попытке с правильными значениями и восемь записей операций. Aiohttp также автоматически повторял идемпотентный PUT после разрыва: прокси видел 16 успешных upstream-ответов для восьми команд, дублей всё равно нет.
- В тестовой базе на завершающей проверке 1363 записи операций, ни одной с незаполненным `response_json`. Это проверка журнала, не доказательство доставки команд, которым API отказал.
- Лёгкие авторизованные чтения выдержали 100 запросов/с. Мониторинг PostgreSQL сохранил наблюдаемость во время отказа API. Идемпотентность и защита версий действительно работают в проверенных сценариях.

Общий вывод по связи: **сохранённые сервером данные в проведённых проверках не потерялись; гарантии «все введённые данные при любом обрыве дойдут до сервера» пока нет**. Не проверялись перезагрузка физического устройства, очистка/переполнение браузерного хранилища, длительное отключение питания, восстановление PostgreSQL после аварии и длительная offline-очередь браузера.

## Артефакты, воспроизведение и безопасность

- `bounded-summary.json`, `bounded-requests.jsonl` — основные ограниченные прогоны; `mutation-journal.jsonl` — тела синтетических команд для восстановления.
- `differential.json`, `admission-experiment.json`, `stack-experiment.json` — контрольные эксперименты; `business_stack-stderr.log` — снимок ожидающих рабочих потоков.
- `judge-faults.json`, `sql-profile.json`, `prometheus-series.json` — проверка судей, количество SQL, сохранённые ряды Prometheus. Отдельные `.prom` и логи — дополнительные свидетельства исследовательского прогона.
- `summary.json` и `requests.jsonl` относятся к первоначальному исследовательскому HTTPX-прогону; только baseline завершён корректно. Они не подменяют основные результаты.
- Скрипты `scripts/load_probe.py`, `load_scenarios.py`, `load_diagnostics.py`, `load_faults.py`, `load_export_metrics.py` сохранены. Они рассчитаны на специально подготовленную одноразовую копию с фиксированным именем `parkrock_load_20260906`; **не переключать их на рабочую базу**. Для нового воспроизведения требуется заново создать эту копию через `pg_dump`/`pg_restore`, добавить синтетическую fixture, запустить временный Prometheus по сохранённому `prometheus.yml`; генератор использует также aiohttp. `load_probe.py` содержит первоначальный исследовательский сценарий, а ограниченный основной запуск — `load_scenarios.py`.
- Рабочие участники сверены с исходной копией: все 6 записей совпали побайтно в каноническом JSON-агрегате, контрольная сумма `32bd3c736f002a5dcad156ee9777e622`. Рабочее событие осталось `preparation`, версия 57, 10 сетов, 20 трасс. В рабочем API выполнялись только проверки и вход тестового администратора, оставивший штатную запись аудита.
- Временные процессы, Prometheus и копия БД удалены после экспорта результатов. Рабочие volumes и пользовательские записи сохранены; рабочий API отвечает, обе штатные цели Prometheus имеют состояние `up`. Состояние очистки зафиксировано отдельно в `cleanup.json`. Зависимость генератора закреплена в `scripts/requirements-load.txt`.
