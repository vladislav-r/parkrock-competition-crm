# ParkRock Hub: состояние проекта

## Назначение

API-first система проведения скалолазного фестиваля:

- публичные онлайн-результаты без авторизации;
- защищенная административная часть;
- самостоятельной регистрации и личного кабинета участника нет.

Актуальное ТЗ: `C:\Users\admin\Documents\Obsidian Vault\ТЗ ParkRockHUB`.
Последние согласованные корректировки: `09-правки-интерфейса-и-данных-02-09-2026.md` в этой папке; при расхождении с документами 01–08 он имеет приоритет. Для остальных новых требований сохраняет силу `08-принятые-решения-по-правкам.md`.

Публичный интерфейс финала:

- после запуска финала вкладка `Финал` доступна для участвующей категории сразу, даже до назначения трасс и появления первых результатов;

- мобильная таблица финала уплотнена: второстепенные столбцы скрываются, а основной результат требует только минимальной горизонтальной прокрутки;
- обозначения категорий сокращены до фиксированных меток вида `М 10-12` / `Д 15-16`, кнопки `Сеты` и `Результаты` используют единый акцентный стиль.

Единый интерфейс сотрудников:

- администраторы, секретари, главные судьи и судьи на трассе входят через одну форму `/admin`; адрес `/judge` без сессии перенаправляет на единый вход, а после авторизации роль открывает своё рабочее место;
- административная часть переведена на светлую высококонтрастную тему; рабочие разделы упорядочены по процессу соревнования, а настройки отделены в группу `Система`.

Дополнительные проверки заявок и клубов:

- переименование в существующую пару «название + представитель» блокируется; объединение выполняется отдельным меню клуба с правом `clubs.merge` и резервной копией (см. блок от 10.09.2026 ниже);
- возраст участника на дату фестиваля ограничен диапазоном 0–99 лет как для ручного добавления, так и для импорта;
- в ручной индивидуальной заявке клуб и связанный с ним представитель выбираются из справочника, а размер мерча — из фиксированного списка `XS`–`3XL` или варианта без заказа.

Резервные копии:

- в группе `Система` появился отдельный раздел `Резервные копии`, доступный по праву `backups.manage` (по умолчанию администратору);
- администратор может создать, загрузить, скачать, проверить и удалить PostgreSQL-дамп; старые файлы из каталога `backups` подхватываются автоматически;
- проверка действительно восстанавливает дамп во временную базу, показывает дату, размер, стадию фестиваля, ключевые счётчики и их отличие от текущей базы, сохраняет SHA-256 и очищает временную базу;
- восстановление требует двух шагов и точной контрольной фразы, предварительно создаёт страховочную копию текущей БД и атомарно переключает заранее восстановленную базу;
- при ручном восстановлении и откате этапа текущие сеты, их даты, время, вместимость, статусы и распределение участников по стартовым номерам сохраняются поверх восстановленной копии;
- операции и отказы доступа записываются в аудит; серверный скрипт поддерживает тип `automatic` без ограничения количества копий.

Финальные корректировки фестивального процесса:

- `preparation` — отдельный явный этап; до нажатия `Начать квалификацию` событие и его резервные копии отображаются как `Подготовка`;

- после запуска квалификации backend ежечасно создаёт подписанные текущим этапом резервные копии без лимита хранения;
- публичное число пройденных трасс скрыто, а карточка с деталями по трассам управляется глобальным переключателем и по умолчанию закрыта;

- перед подтверждением квалификации, запуском финала и подтверждением финала интерфейс перечисляет возрастные группы без результатов и требует явного подтверждения; подтверждение финала можно отменить с возвратом к сохранённому состоянию финала;
- применены миграции `0017_final_adjustments` и `0018_preparation_stage`; реальное создание и восстановительная проверка дампа подтверждены копией `backups/climbhub-20260904-161840-validation.dump`.

## Стек и адреса

- frontend: Next.js + TypeScript, `http://localhost:3000`;
- админка: `http://localhost:3000/admin`;
- backend: FastAPI, `http://localhost:8001`;
- OpenAPI: `http://localhost:8001/docs`;
- база: PostgreSQL в Docker;
- Redis не используется.

Запуск при работающем Docker Desktop:

```powershell
.\scripts\start-dev.ps1
```

Обычный запуск применяет миграции Alembic и не заполняет базу демоданными. Демоданные создаются только явной командой `scripts\seed-demo.ps1 -ConfirmDemoData`.

Production-развёртывание на одном VPS подготовлено в `docker-compose.prod.yml`:

- `caddy`, `frontend`, `backend` и `postgres` запускаются отдельными контейнерами;
- наружу публикуются только `80/443`, маршруты `/api/*`, `/health`, `/docs` и `/openapi.json` проксируются в backend, остальные — во frontend;
- PostgreSQL изолирован во внутренней Docker-сети, данные, backup-файлы и TLS-состояние находятся в отдельных volumes;

## Правила предметной области

Управление сбросом соревнования:

- в `Настройки → Соревнования` администратор может отдельно сбросить этап, результаты квалификации и финала, настройки финала, заявки, участников, статусы ресепшена, клубы, сеты и их статусы, трассы, категории, назначения судей и публичную детализацию;
- перед любым сбросом создаётся проверенная страховочная копия с комментарием;
- общий сброс удаляет все соревновательные данные, но сохраняет учётные записи, права, журнал и резервные копии; после него создаётся отдельный нулевой снимок;
- в подтверждении кнопка `Отмена` красная и визуально главная, а `Сбросить` — нейтральная серая.

- Участники регистрируются заранее и импортируются уже назначенными в сеты.
- Стандартный коллективный импорт принимает XLSX-шаблон заявки фестиваля: название команды и представитель обязательны в шапке, телефон необязателен; в строках обязательны `Фамилия`, `Имя`, `Год рождения`, `Пол`, `Разряд`, `Сет`, а `Отчество` необязательно. Название команды переносится как клуб, представитель — всем участникам заявки.
- Возрастная категория определяется по календарному году фестиваля и году рождения: день и месяц рождения не учитываются.
- Год рождения хранится отдельным полем; для коллективной заявки в интерфейс и предпросмотр передаются только четыре цифры, без технической даты и времени.
- Дубликат определяется по ФИО и дате рождения; при ошибке импорт целиком отменяется.
- Стартовый номер назначается автоматически и уникален внутри мероприятия.
- Вместимость задается отдельно для каждого сета. Переполнение импорта и ручное добавление в заполненный сет возможны только после отдельного подтверждения пользователя с правом управления участниками.
- Сет может иметь отдельную дату; в списках сеты сортируются по дате, затем по времени начала; записи без даты идут после них.
- Пришедшему участнику подтверждают вход. До входа его можно перенести в другой сет с подтверждением.
- Трассы общие для всех сетов и групп. Учитывается только факт прохождения, без попыток, зон и флэша.
- Карточка результатов по умолчанию доступна только для просмотра. Секретарь нажимает `Изменить`, формирует локальный черновик и сохраняет весь набор кнопкой `Подтвердить`.
- До подтверждения карточки изменения нигде не отображаются. После подтверждения рейтинг и публичные страницы обновляются.
- Подтверждение сета завершает и блокирует его. Для исправления сет повторно открывают.
- Финалисты: настроенное для категории количество плюс все участники с равным результатом на проходной границе; если результатов меньше лимита, проходят все показавшие результат.
- Рабочее место судьи на трассе открывает финалистов и принимает результаты только после фактического запуска финала; при откате старый локальный кэш блокируется и очищается.
- Значение `Количество финалистов = 0` отключает финал для категории, но не отключает обязательное подтверждение ее квалификации и расчет медалей финишеров.

## Безопасность данных

- Рабочие данные находятся в PostgreSQL volume `climbhub_postgres`.
